# Native ARM scanner research — 2026-10-05

HP's [HPLIP supported-device table](https://developers.hp.com/hp-linux-imaging-and-printing/supported_devices/index) lists the LaserJet Professional M1136 as a USB multifunction printer with scanning support. Its [binary plug-in table](https://developers.hp.com/hp-linux-imaging-and-printing/binary_plugin.html) marks the M1136 plug-in **required** for both scanning and printing. HP describes that plug-in as proprietary software that cannot be open sourced. OpenPrinting's [HPLIP Printer Application](https://github.com/OpenPrinting/hplip-printer-app) still lists scanning support as unfinished.

The connected device is USB VID `03f0`, PID `042a`. macOS `ioreg` shows separate interfaces: `Printer` number 0 (class 7), `HP EWS` number 1 (vendor-specific), and `HP SCAN` number 2 (vendor-specific, two endpoints). This establishes a distinct scan interface, but does not reveal its command protocol.

The installed Apple-distributed `HP M1130_M1210 Scanner.app` matches VID `03f0`/PID `042a` and is an x86_64/i386 binary with no arm64 slice. It remains the working Image Capture path on this Mac, but its architecture does not provide a native ARM implementation.

The official [HPLIP 3.25.8 source archive](https://sourceforge.net/projects/hplip/files/hplip/3.25.8/) lists `hp_laserjet_professional_m1136_mfp` in `data/models/models.dat` with `scan-type=8`, `scan-src=1`, and `plugin=0`. Its `io/hpmud/hpmud.h` identifies type 8 as `MARVELL2` and names the `HP-MARVELL-SCAN` channel. Yet `scan/sane/marvell.c` unconditionally calls `bb_load(..., SCAN_PLUGIN_MARVELL)` and dispatches scan operations through `bb_open`, `bb_start_scan`, `bb_get_image_data`, and completion functions from that library. The public `scan/sane/marvelli.h` shows the function signatures and shared session buffer, but not the request/response framing. No `bb_marvell` implementation is present in the source archive. The model's `plugin=0` flag therefore conflicts with both the scanner code's dependency and HP's published plug-in requirement. Treat the dependency shown by code as decisive until a scan without the plug-in is demonstrated.

This evidence does not establish that an independent open-source ARM scanner backend is impossible, but HPLIP's open-source scanner code alone is incomplete for this model. The existing compatibility scanner works and remains the practical fallback. No native scanner code or protocol claim is included in this repository yet.

Next: study the Marvell2 transport and the `bb_*` function contract, then determine whether the protocol can be implemented independently using permitted local observations. Do not distribute HP's binary plug-in in this project or claim native scanning until an independent ARM scan-to-file test succeeds.
